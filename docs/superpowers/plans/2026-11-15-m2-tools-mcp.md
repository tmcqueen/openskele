# Milestone 2: Tools and the Private MCP Server Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One tool registry (built-in and plugin tools) served over MCP on a private local socket, reachable only through `skele-mcp-bridge` with a valid grant token.

**Architecture:** `tools/` in `skele-core` holds the registry and built-in tools, which wrap existing `Workbench` methods. Plugins add tools via a new `tool/call` protocol request. `mcp/service.rs` adapts the registry to `rmcp` over any byte stream; `mcp/socket.rs` accepts local-socket connections that present a grant token; the bridge binary pipes an agent's stdio to that socket.

**Tech Stack:** Rust, `rmcp` (server + client in tests), `interprocess` (local sockets, tokio), `jsonschema` (already a dependency), `getrandom` (tokens); TypeScript and .NET SDKs.

**Spec:** `docs/superpowers/specs/2026-11-15-app-bars-agents-design.md` (Milestone 2). ADRs: `docs/adr/0003-private-mcp-server-via-bridge.md`, `docs/adr/0004-plugin-tools-via-protocol.md`, `docs/adr/0006-tool-approval-delegated-to-agent.md`.

**Depends on:** Milestone 1 merged (layout, `Workbench::new_terminal`, `TerminalManager::read`).

## Spike notes (Task 1, 2026-11-15)

Confirmed in a throwaway crate: an rmcp server over `tokio::io::duplex`, and
over an `interprocess` local socket reached by a client through a stdio pipe
binary spawned with rmcp's child-process transport.

- Crates: `rmcp = { version = "3.10.0", features = ["server"] }` in skele-core;
  tests and the bridge test add `"client", "transport-child-process"`.
  `interprocess = { version = "2.4.8", features = ["tokio"] }`.
- Server: `impl rmcp::ServerHandler for X` (`Clone`), with
  - `fn get_info(&self) -> ServerInfo { InitializeResult::new(ServerCapabilities::builder().enable_tools().build()) }`
  - `async fn list_tools(&self, _: Option<PaginatedRequestParams>, _: RequestContext<RoleServer>) -> Result<ListToolsResult, ErrorData>`
    returning `ListToolsResult::with_all_items(tools)`
  - `async fn call_tool(&self, r: CallToolRequestParams, _: RequestContext<RoleServer>) -> Result<CallToolResponse, ErrorData>`
    returning `CallToolResult::success(vec![ContentBlock::text(..)]).into()` or `CallToolResult::error(..)`; unknown tool → `Err(ErrorData::method_not_found::<CallToolRequestMethod>())`.
- Tools: `Tool::new(name, description, Arc<JsonObject>)`, `.with_title(..)`,
  `.annotate(ToolAnnotations::new().read_only(b).destructive(b))`.
- Serving: `handler.serve((reader, writer)).await?` → `RunningService`; `.waiting().await` returns when the peer disconnects. Ending a connection from the server: `running.cancel().await`.
- Client (tests): `().serve(transport).await?`; `client.list_all_tools()`, `client.call_tool(CallToolRequestParams::new(name).with_arguments(obj))`, `client.cancel()`. Transport: `rmcp::transport::TokioChildProcess::new(tokio::process::Command)`.
- Local socket: `ListenerOptions::new().name(path.to_fs_name::<GenericFilePath>()?)`, `.mode(0o600)` (unix `ListenerOptionsExt`, applied before bind: no umask race), `.create_tokio()`; `listener.accept().await` → stream; `tokio::io::split(stream)`. Client: `LocalSocketStream::connect(name).await`.

## Global Constraints

- **Seams (ADR-0003), mandatory:**
  1. `mcp/service.rs` takes any `AsyncRead + AsyncWrite` and a `Grant`; it never names a socket, pipe or port.
  2. Tokens are `Grant`s (`GrantKind::AgentSession { session_id } | External`), never ACP sessions. Only `AgentSession` grants are issued in this milestone.
  3. Tool handlers receive `ToolCall { arguments, grant }` and nothing that refers to an ACP session.
- No TCP listener anywhere. Unix socket file mode `0600`, in `$XDG_RUNTIME_DIR` if set, else `std::env::temp_dir()`, named `openskele-<pid>.sock`; removed on shutdown.
- Token: 32 bytes from `getrandom`, lowercase hex (64 chars). Handshake: the bridge's first line on the socket is the token followed by `\n`; a token that `GrantStore::check` rejects closes the connection without a reply.
- Bridge env vars: `SKELE_MCP_SOCKET`, `SKELE_MCP_TOKEN`. Bridge path: `SKELE_MCP_BRIDGE` if set, else `skele-mcp-bridge` (`.exe` on Windows) beside `std::env::current_exe()`.
- Tool names match `^[a-z][a-z0-9_]*$`; duplicate names are rejected like duplicate commands.
- `PROTOCOL_VERSION = "0.2.0"`; sample manifests `"protocol": "0.2"`.
- `Grant.confirm_mutations` exists, is `false` for agent grants, and nothing reads it (ADR-0006).
- Tool failures (bad arguments, plugin not starting, plugin error, unknown document) are returned as `ToolCallResult { is_error: true, content: [text] }`, not as JSON-RPC errors; only an unknown tool name is a protocol error.
- Each task ends with `cargo test --workspace`, clippy `-D warnings`, `bun run typecheck`, and (for SDK tasks) `dotnet build`.

## Review Focus

- Arguments that fail the tool's `inputSchema` (wrong type, missing required field): `is_error: true` with the validation message; the handler is not called (test in Task 3).
- A plugin tool whose plugin cannot start, or whose plugin has no handler for a declared tool: `is_error: true` naming the plugin; later calls still work (tests in Tasks 4 and 5).
- A grant revoked while its connection is open: the next `tools/call` fails and the connection closes (test in Task 7).
- Two plugins contributing the same tool name, or a name like `hello.greet`: the second/invalid install fails and none of that plugin's contributions remain (test in Task 4).
- Two bridge connections with different grants at once: calls on each see their own grant (test in Task 7).
